# #619 — Dashboard mount after ADR-0035: measuring one pricing pass per read

- **Date:** 2026-08-03
- **Issue:** [#619](https://github.com/peshay/portfolixir/issues/619) —
  ADR-0035 hard requirement 5 ("measured, not asserted"). This is the
  after-measurement of the change; the before-measurement is
  `619-dashboard-mount-measurement-2026-07-31.md`.
- **Decision under test:** [ADR-0035](../../docs/decisions/0035-one-pricing-pass-per-read.md)
  — market data preloaded once per read into an explicit pricing context and
  threaded into every valuation and allocation in that read.
- **Scope:** `DashboardLive.start_loading/1`'s single `start_async(:overview,
  ...)` block, replicated verbatim in the dashboard's evaluation order.

## Methodology

Same shape as the 2026-07-31 report, extended to an A/B:

- Throwaway measurement scripts (local scratchpad only, deliberately not
  committed) replicate the async block's computations **verbatim and in the
  dashboard's evaluation order**, timing each step with `:timer.tc/1`.
- **One fresh BEAM VM per run** (`mix run --no-start`, application started in
  the script). Every run starts with an empty ADR-0032 ETS memo and a cold
  BEAM; nothing survives between runs.
- **Two checkouts, one database.** The measurement is read-only, so the
  baseline checkout and the branch checkout run the *same* script against the
  *same* seeded database. The script is variant-agnostic: it builds and
  threads a pricing context only where the checkout has one
  (`Code.ensure_loaded?/1`), so each side runs its own dashboard block, not a
  translated one.
- Two modes, both with a fresh VM per run:
  - **warm** (7 runs per side): the ADR-0032 §5 boot warmup is run to
    completion first, then the block is timed. The state a real mount sees.
  - **cold** (5 runs per side): the block runs immediately after boot, before
    any warmup — the memo is empty, so the TTWROR step pays the full walk.
- **Query counts** are measured in the same runs by counting
  `[:portfolixir, :repo, :query]` telemetry events per step. This is the
  quantity ADR-0035 actually attacks, so it is reported next to the times.
- Environment hygiene, as in the 2026-07-31 report:
  - dev configuration, local PostgreSQL 16, Elixir 1.18.3 / OTP 27, 4 cores;
  - logo discovery, quote sync and rate sync **disabled** (no network calls);
  - the boot-time warmup GenServer disabled and, in warm mode, invoked
    synchronously instead, so it never races the measurement;
  - Logger raised to `:warning`.
- PostgreSQL stays up across runs, so its buffer cache is steady-state warm.
- Not measured: `assign_stale_ttwror/1` (the synchronous ADR-0032 §6 read in
  `mount/3`), and the Wealth page's own async block. The Wealth page gets the
  same one-context treatment in the same change, but it was not separately
  benchmarked — no claim is made about it here.

### Baseline choice — a recorded deviation

The 2026-07-31 report measured `main` of that day. This report's baseline is
**the branch's own parent commit** (`c5e33e5`, the commit that records
ADR-0035), not today's `origin/main`. The branch sits 12 commits ahead of
`main` with the Sprint 3 lane work — including the ADR-0033 per-position P&L
decomposition, which changes the ledger read paths the dashboard touches.
Measuring against `main` would have credited (or blamed) this change with
those 12 commits' cost. The baseline used here isolates exactly this diff.
Absolute numbers are therefore **not** comparable with the 2026-07-31 report;
the ratios and the query counts are the result.

## Synthetic dataset (synthetic all the way down)

Generated by a deterministic seed script (scratchpad only, not committed)
through the public context APIs (`Catalog`, `Portfolios`, `Ledger`,
`Classifications`, `Targets`, `Fx`, `Quotes.upsert_many`). Nothing resembles
any real portfolio; names are `Synthetic Portfolio N` / `Synthetic Security
NNN` and every figure comes from an integer pseudo-random walk.

| Entity | Count | Shape |
| --- | --- | --- |
| Portfolios | 5 | all EUR base, each with 2 cash-account/depot pairs |
| Cash accounts / depots | 10 / 10 | `free_cash` role |
| Securities | 60 | 45 EUR + 15 USD; 6 with no persisted asset class; all without logo |
| Quotes | 58,268 rows | 4 years of business-day closes (2022-08 → 2026-07) for 56 securities; 6 of those stale (history ends ~2 months early); 4 securities with no quotes at all |
| FX rates | 1,461 | daily synthetic EUR→USD hub rates over the same window |
| Transactions | 810 | per portfolio: 2 deposits + 144 monthly buys (3/month over 48 months, alternating depots, incl. cross-currency USD buys with ADR-0015 settlement legs) + 16 quarterly sells |
| Classification | 1 custom ("Synthetic Strategy") | 6 root categories, every security assigned |
| Target plans | 5 (one per portfolio) | equal 16 % category targets against an unequal actual mix, so several categories drift beyond ±5 pp and 5 alerts fire |
| Derived positions | 300 | (depot, security) pairs the block prices |

Sanity payload, identical on **every run of both variants** (this is the
Decimal-identity check running on the benchmark dataset, not only in the test
suite): total value 268,940.88, total cash 197,747.15, total with cash
466,688.03 (synthetic EUR), 300 positions, 0 unvalued, 20 trade-priced, YTD
TTWROR `0.046950674802621454130764296771328`, 5 drift alerts with identical
drift values to the last digit, data quality 10 stale-quote / 6 class-less /
60 logo-less of 60.

## Results — warm memo (the state a real mount sees), 7 runs per side

Times are per-step medians (min–max) across runs; each run is a fresh VM.
"Queries" is the median number of Ecto queries that step issued.

| Step | Baseline median | Baseline queries | After median | After queries |
| --- | --- | --- | --- | --- |
| Prelude (default view + base currency) | 2.9 ms (2.3–5.2) | 3 | 3.0 ms (2.7–3.9) | 3 |
| **Pricing context (one pass)** | — | — | **88.7 ms (86.5–89.8)** | **35** |
| **View valuation** | **466.2 ms (452.9–490.8)** | **1,265** | **15.9 ms (14.9–16.7)** | **6** |
| YTD TTWROR (memoized, ADR-0032) | 14.2 ms (12.0–21.0) | 0 | 14.1 ms (13.2–18.3) | 0 |
| **Drift alerts (5 × allocation)** | **588.0 ms (514.8–641.8)** | **1,342** | **128.8 ms (119.3–133.3)** | **67** |
| Data quality | 11.7 ms (10.1–12.2) | 4 | 11.2 ms (9.8–12.5) | 4 |
| **Whole async block** | **1,104.6 ms (995.1–1,153.6)** | **2,614** | **264.7 ms (247.8–268.4)** | **115** |

- Whole block: **4.2× faster** (−840 ms median), **22.7× fewer queries**
  (2,614 → 115).
- Valuation-shaped work only (pricing context + view valuation + drift
  alerts): 1,054.2 ms → 233.4 ms, **4.5×**.
- The pricing context is a real new line item, not free: 88.7 ms and 35
  queries that the baseline paid inside the valuation instead. It is counted
  in the "after" total above.
- The two untouched steps (memoized TTWROR, data quality) are unchanged
  within run-to-run noise, as expected.

The cold block improves by only **9 %** because the unmemoized TTWROR walk is
~86 % of it and ADR-0035 deliberately does not touch that walk. The TTWROR
step reads 1.3 % *higher* on the after side, which is run-to-run noise: the
min–max ranges overlap heavily (7,527–7,888 vs 7,658–7,961) and no code on
that path changed. The pricing-context step is nearly 2× its warm cost for
the same reason the baseline's first valuation was: nothing has read the
transaction tables yet.

## Finding

**On the warm mount — the state almost every real mount sees — the async
block drops from ~1,105 ms to ~265 ms (4.2×) and from 2,614 database queries
to 115 (22.7×), with an identical sanity payload on every run.** (That payload
is the one defined above — totals, position and alert counts, TTWROR to 30
digits, the five drift values — not the full read output; byte-identity of the
complete result is what the test suite pins, not what this benchmark
measures.) The two steps
ADR-0035 targeted carry the whole win: the view valuation falls 466 ms → 16 ms
and the five-allocation drift loop 588 ms → 129 ms, at the cost of one 89 ms
preloading step that replaces work the baseline did per row.

The query-count reduction is the honest headline, because it is what the
decision actually changed: the block no longer asks the same small questions
hundreds of times. 2,614 → 115 is a structural result, not a tuning result,
and it does not depend on this machine.

**Where the win is smaller than one might hope, stated plainly:**

- **The cold mount barely moves (9 %).** The unmemoized TTWROR walk dominates
  it and is explicitly out of scope here (ADR-0032 owns it). ADR-0035 makes a
  *fresh valuation* cheap; it does not make a *fresh performance series*
  cheap.
- **The remaining 265 ms is not evenly attackable.** After the change the
  block is: pricing context 89 ms (34 %), drift alerts 129 ms (49 %), TTWROR
  14 ms, data quality 11 ms, prelude 3 ms. The drift step is still the
  largest single item — what remains in it is allocation-specific work
  (classification joins, target plans, the category roll-up), not repeated
  pricing. Attacking it further is a different change with a different
  decision behind it.
- **67 queries still leave the drift loop** (13 per portfolio), and 35 the
  pricing context. Neither is a per-row count any more; both are per-read
  counts that grow with portfolios and currencies, not with positions.
- **Absolute times are from a 4-core container** and matter less than the
  ratios and the query counts. A different dataset shape moves the absolute
  numbers: position count (300 here) drives the baseline's per-row cost and
  therefore the size of the win, while portfolio count drives the residual
  drift-loop cost.

Nothing in the block was memoized, cached or persisted to get this: ADR-0004
and ADR-0032 are untouched, and the identical sanity payload across all 24
runs of both variants is the same acceptance criterion the test suite pins
(ADR-0035 hard requirement 1).
