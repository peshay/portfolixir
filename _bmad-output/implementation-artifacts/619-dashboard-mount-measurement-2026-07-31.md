# #619 — Dashboard mount: measuring the three remaining async computations

- **Date:** 2026-07-31
- **Issue:** [#619](https://github.com/peshay/portfolixir/issues/619) — split out
  of #562; measurement only, explicitly no optimisation and no pre-diagnosis.
- **Baseline:** post-#562. ADR-0032 (memoized daily TTWROR walk, boot warmup,
  serve-last-known) is merged and active during these measurements.
- **Scope:** `DashboardLive.start_loading/1` runs one `start_async` block that
  computes four things, in this evaluation order:
  1. **View valuation** — `Valuation.for_view/2` inside `wealth_card/1`
  2. **YTD TTWROR** — `Performance.for_portfolio/2` inside `wealth_card/1`
     (the one ADR-0032 already covers)
  3. **Drift alerts** — `Allocation.for_portfolio/3` per portfolio
  4. **Data quality** — `Catalog.list_securities_with_metrics/1` plus the
     missing-logo count

  This report measures which of the **remaining three** (1, 3, 4) dominates a
  cold mount. No code was changed.

## Methodology

- Throwaway measurement scripts (local scratchpad only, deliberately not
  committed) replicate the async block's computations **verbatim and in the
  dashboard's evaluation order**, timing each step with `:timer.tc/1`.
- **One fresh BEAM VM per run** (`mix run --no-start`, application started in
  the script). Every run therefore starts with an empty ADR-0032 ETS memo and
  a cold BEAM — nothing survives between runs.
- Two modes, both with a fresh VM per run:
  - **cold** (7 runs): the block runs immediately after boot, before any
    warmup — the memo is empty, so the TTWROR step pays the full walk. This is
    the "restart, open dashboard before the §5 warmup finishes" mount.
  - **warm** (3 runs): the ADR-0032 §5 boot warmup (`Warmup.warm/0`) is run to
    completion first, then the block is timed. This is the documented post-#562
    steady state — the state almost every real mount sees.
- Environment hygiene:
  - dev configuration, local PostgreSQL, Elixir 1.18.3 / OTP 27, 4 cores;
  - logo discovery, quote sync and rate sync **disabled** (no network calls);
  - the boot-time warmup GenServer disabled and, in warm mode, invoked
    synchronously instead, so it never races the measurement;
  - Logger raised to `:warning` — dev logs every Ecto query at debug level,
    which would otherwise be measured as computation time.
- PostgreSQL stays up across runs, so its buffer cache is steady-state warm.
  The numbers measure query + Elixir computation cost, not first-ever disk
  I/O — which matches a self-hosted always-on instance.
- Not measured: `assign_stale_ttwror/1` (the synchronous ADR-0032 §6 read in
  `mount/3`) — it is part of the #562 machinery, not one of the four async
  computations.

## Synthetic dataset (synthetic all the way down)

All data was generated by a deterministic seed script through the public
context APIs (`Catalog`, `Portfolios`, `Ledger`, `Classifications`,
`Targets`, `Fx`, `Quotes.upsert_many`). Nothing resembles any real portfolio;
names are `Synthetic Portfolio N` / `Synthetic Security NNN`.

| Entity | Count | Shape |
| --- | --- | --- |
| Portfolios | 5 | all EUR base, each with 2 cash-account/depot pairs |
| Cash accounts / depots | 10 / 10 | `free_cash` role |
| Securities | 60 | 45 EUR + 15 USD; 7 with no persisted asset class; all without logo |
| Quotes | ~55,000 rows | 4 years of business-day closes (2022-08 → 2026-07) for 50 securities; 6 securities stale (history ends 60 days early); 4 with no quotes |
| FX rates | 1,460 | daily synthetic EUR→USD hub rates over the same window |
| Transactions | 800 | per portfolio: 2 deposits + 144 monthly buys (3/month over 48 months, alternating depots, incl. cross-currency USD buys with settlement FX) + 14 quarterly sells |
| Classification | 1 custom ("Synthetic Strategy") | 6 root categories, every security assigned |
| Target plans | 5 (Gesamt, one per portfolio) | equal 16% category targets against an unequal actual mix, so several categories drift beyond ±5 pp and the alerts path does real work (5 alerts fire) |

Sanity checks passed on every run: valuation total ≈ EUR 9.88 M (synthetic),
YTD TTWROR computed, 5 drift alerts, data quality = 10 stale-quote / 7
class-less / 60 logo-less of 60 securities.

## Results

Times are per-step medians (min–max) across runs; each run is a fresh VM.

### Post-#562 steady state (warm memo — the state a real mount sees), 3 runs

| Step | Median | Min–max | Share of async block |
| --- | --- | --- | --- |
| `Settings.default_view_id` + card prelude | 3.2 ms | 3.0–3.4 | ~1% |
| **View valuation** (`Valuation.for_view`) | **167.8 ms** | 155.9–192.4 | **43%** |
| YTD TTWROR (memoized, ADR-0032) | 8.3 ms | 7.8–9.0 | 2% |
| **Drift alerts** (5 × `Allocation.for_portfolio`) | **188.7 ms** | 178.0–199.1 | **49%** |
| Data quality | 9.2 ms | 8.3–9.6 | 2% |
| **Whole async block** | **388.0 ms** | 353.0–402.6 | 100% |

Among the three remaining computations only (excluding the memoized TTWROR):
drift alerts **52%**, view valuation **46%**, data quality **2%**.

### Cold boot before warmup (empty memo), 7 runs

| Step | Median | Min–max | Share of async block |
| --- | --- | --- | --- |
| `Settings.default_view_id` + card prelude | 13.0 ms | 11.3–17.8 | ~1.5% |
| View valuation | 277.8 ms | 243.1–320.6 | 32% |
| YTD TTWROR (full walk, memo empty) | 345.3 ms | 302.2–379.0 | 40% |
| Drift alerts | 247.6 ms | 223.3–270.5 | 29% |
| Data quality | 10.7 ms | 9.2–12.2 | 1% |
| **Whole async block** | **867.1 ms** | 816.7–972.2 | 100% |

### Decomposition of the drift step (warm, single fresh VM)

`Allocation.for_portfolio` per portfolio: 85.7 / 55.8 / 51.5 / 42.0 / 40.5 ms
(first call pays some shared warm-up). A single `Valuation.for_portfolio` in
the same VM: ~31 ms. A single `Valuation.for_view(nil)`: ~177 ms.

## Finding

**No single computation of the three dominates alone: drift alerts (~49%) and
the view valuation (~43%) together are ~92% of the post-#562 async block, in
roughly equal parts (drift ~1.1× valuation). Data quality is noise (~2%,
~9 ms).**

The structurally more useful reading: **both heavy steps are the same kind of
work.** `Allocation.for_portfolio` embeds a fresh per-portfolio
`Valuation.for_portfolio` (plus classification/target joins), and
`Valuation.for_view` is the deduplicated cross-portfolio valuation. One
dashboard mount therefore prices holdings **six times** (1 view-wide + 5
per-portfolio) — valuation-shaped work is ~95% of the remaining-three time.
On the truly cold path (restart, before warmup) the unmemoized TTWROR walk is
still the single largest step (40%), confirming ADR-0032 addressed the right
first target; its memo drops that step from ~345 ms to ~8 ms (~40×).

## Sensitivity notes — how the shape of the data moves these numbers

- **Portfolio count** moves the drift step linearly: it is a per-portfolio
  loop, each iteration carrying its own valuation. At 1 portfolio the drift
  step shrinks to roughly a single allocation call (~40–85 ms) and the view
  valuation becomes the clear dominator; at 10+ portfolios drift dominates
  outright.
- **Held-position count and quote depth** move both heavy steps together,
  since both are priced-holdings walks over transactions + latest quotes + FX.
- **Security count** moves data quality, but gently: `attach_metrics` is one
  SQL statement with index-backed lateral joins, and the logo count is one
  query. At 60 securities it costs ~9 ms; it would take an implausibly large
  catalog for this step to matter.
- **Views/buckets:** measured with no default view (Everything scope). A
  bucket-scoped default view adds scope-filtering work to every valuation;
  not measured here.
- **Postgres cache state:** a first-mount-after-host-reboot (cold OS page
  cache) would add disk I/O on top of every step; the ranking between the
  steps is unlikely to change since they read largely the same tables.
- **Absolute times** are from a 4-core container and matter less than the
  ratios.

## Options this measurement informs (decision explicitly downstream)

Per the issue, no option is chosen here; the numbers constrain the choice:

1. **Extend ADR-0032-style memoisation to valuation** — attacks ~92% of the
   block at once, because the drift step's cost *is* five valuations; but
   ADR-0032's Consequences explicitly deferred caching valuation/allocation as
   a separate decision with its own risk.
2. **Narrower queries** — plausible inside the allocation path (e.g. sharing
   one holdings/pricing pass across the per-portfolio loop, or between
   `for_view` and the loop, instead of re-deriving it six times); the
   data-quality queries need nothing.
3. **Different page composition** — splitting the one async block into
   per-section asyncs would not reduce total work but would let the cheap
   sections (data quality, ~9 ms; memoized TTWROR, ~8 ms) paint ~380 ms
   earlier and the two heavy cards resolve independently.

Any of these is a separate, reviewed decision; this report only supplies the
measured baseline.
