Two states, not one

A number that is not on screen yet is in one of two different situations, and they want different affordances. Pending means the value is unknown: a query is running, the valuation is being recomputed, and this lasts seconds. Settling means the value is already known and is being drawn — the ~600 ms count-up from DESIGN.md › Motion. Today the app treats both as one thing: … for pending, nothing for settling.

Sections 2 and 3 offer separate vocabularies for those two states, section 4 for the allocation sunburst, which is a third case again (many values landing over time rather than one). Every option carries a stable ID. Pick one per section.

All figures are synthetic sample data. Inter and JetBrains Mono cannot be embedded offline, so the system font stack stands in for both — judge the behaviour, not the letterforms. Explanatory prose is English; strings inside the mock cards are German, as shipped.

Pending options: what each costs to build and what it risks
IDWhat it isBuild cost (no bundler)Risk
P1 Typographic skeleton. Shimmer bar exactly as wide and tall as the number it becomes; the label stays fully rendered. Low. Pure CSS — .section-skeleton's gradient already exists in app.css; this is the same keyframe at text size. The footprint comes from rendering the expected string with color: transparent, so no magic width constant. The footprint is a guess until the value arrives; a 6-digit guess for a 9-digit value still shifts layout. Shimmer at 30 px height is a large moving object on a calm surface — four of them on one row is busy.
P2 Last known, dimmed. Previous value in --color-text-muted plus the proposed cue: spinner + “Letzter Stand … · wird neu berechnet”. Low, where a prior value exists — the dashboard already carries @stale_ttwror for exactly this. Elsewhere it needs a stale cache that does not exist yet, per card. A stale number that looks like a real number. Muted text is the only signal that it is not current, and muted text is also just… text. The date in the cue is load-bearing; if it is ever dropped, this option becomes a lie. Only available on repeat visits — first load falls back to another option, so a choice of P2 is really “P2 plus one of the others”.
P3 Progressive reveal. Label and currency render immediately; the number slot stays empty with a thin indeterminate accent line along its baseline. Low. One pseudo-element sweep, no JS. The reserved slot width has the same guess problem as P1. The moving line sits where an underline would; it can read as a text decoration or a progress bar with a meaning it does not have. Quiet enough that a slow query might not look like anything is happening.
P4 Today's behaviour (control). A bare … in the value slot, as portfolio_live.ex renders it now. None. It is already built. Indistinguishable from an error, an empty result, or a value that is genuinely unavailable — the same … for all three. No indication that anything is in flight, so a stuck query looks identical to a fast one. It is here as the baseline to beat, not as a non-option.

Reduced motion, all four: P1 becomes a flat --color-bg-muted bar (footprint intact, no shimmer); P2's spinner becomes a static half-opacity ring, exactly as app.css already defines; P3's baseline becomes a dashed accent line — dashed reads as indeterminate without moving; P4 is unaffected because it never animated. Toggle the switch in the top bar.

Settling options and their drawbacks
IDWhat it isDrawback
S1 Accent underline. Digits muted during the count; a 2 px accent bar under the number grows 0 → full width and fades out on settle. The bar looks like a determinate progress bar, and it is one — of the animation, not of the computation. If the count-up ever starts before the value is final, the bar becomes a false promise. Adds 2 px + 6 px of reserved height under every number, or the card shifts when it appears.
S2 Digit shimmer. Digits at final colour with a soft accent sweep crossing the glyphs; the sweep stops on settle. Needs background-clip: text, which means the digits are painted by a gradient and color is transparent for the duration — in any engine that fails the @supports test the digits would vanish, so the guard is mandatory. Legibility of a moving gradient on 30 px numerals is the thing to judge here, especially in dark mode.
S3 Pulsing marker. Digits at final colour; a small accent dot right of the value pulses during the count and disappears on settle. The dot appears and then vanishes, which is a layout element with a 600 ms lifetime — either reserve its width permanently or accept a small shift. A pulsing dot next to a number is also the conventional shape for “live/streaming”, which this is not.
S4 Colour resolve only. Digits count up muted and transition to full accent on settle. No added element. Nearly invisible on a fast machine — for 600 ms the only difference is text colour, and muted-vs-accent is a subtle step. Colour alone as a state signal also has to survive the accent switch (coral at 30 px passes, but the muted→coral delta is the weakest of the three accents).

Honest caveat: how much jitter you see depends on the font actually rendering this page. Inter's default figures are proportional, so in the real app the difference is real and this is what it looks like. Some system fallback fonts default to tabular figures, in which case the right card will look almost identical here — the constraint still holds for the shipped surface. Note also that both cards' left edge advances as digits are added; that is digit count, not jitter. The jitter is the non-monotonic wobble at constant digit count.

4 · Progressive sunburst fill

The allocation sunburst is the third case: eleven values landing over time rather than one. Same simplified chart three times — three inner categories, eight leaves — with a different arrival strategy each. Synthetic weights, chosen to sum to 100 %.

F1

Sequential sweep

Segments appear clockwise as their values arrive. Reads as a scan — you can see the chart being assembled. Drawback: clockwise order is not the order data actually arrives in, so the sweep is choreography pretending to be progress; and the last segment lands ~1.1 s in, which is long for a chart that is otherwise instant.

F2

Rings resolve inward-out

Inner ring first, then the outer. Matches the data's shape — parents are known before children — and matches how the chart is read. Drawback: the intermediate frame is a complete, plausible-looking three-segment donut, which is a different (wrong) chart for ~400 ms. Also the most obviously “animated” of the three.

F3

Fade-in-place

All segments present as muted ghosts from the first frame; each saturates to its real colour when its value lands. The final geometry is visible immediately, so nothing moves and nothing reflows. Drawback: ghost segments already show the true proportions, which means the layout is known before the values are — only honest if the geometry really is known first. Ghost grey at low contrast is also close to the “Unsorted” and “excluded” greys the real chart already uses.

    Reduced motion: all three render the finished chart on load and Replay is a no-op — no stagger, no fade. Colours are the project category palette from portfolio_live.ex (#2563eb, #0d9488, #d97706 and neighbouring shades for the children).

    Sample data. Every figure on this page is invented for the demo — 250.000,00 EUR, the weights below, the booking counts and dates. Nothing here comes from a real portfolio.

    How to answer

    One ID per section, e.g. “P1 + S3 + F3”. Combinations are free — the three states are independent, and picking P2 additionally implies a fallback choice from P1/P3/P4 for first loads. If none of a section's options fits, say so; a “none of these, here is what bothers me” is a usable answer too.
