A — Wertpapier-Detail, Werteachse

  • A makes the token true: {typography.chart-axis} says 9 px and DESIGN.md calls it "9px mono inside SVG"; the build renders 9 viewBox units, which is 9 px only on a 960 px chart. The chart hook already computes the scale for its crosshair (layout_view.ex:768, ChartCrosshair: view.width / svgRect.width); it writes it to --chart-upx and rule ② multiplies. Five values and both dates stay. On a chart under about 760 px the values move inside the plot on their grid lines with a surface halo (rule ③), because the 56-unit gutter is 20 px at 390. Without script the label is exactly today's.
  • B is CSS only: under 560 px a constant (2.9, the scale of a 390 px phone) replaces the measurement, and two of five values go. It fixes the one width it was tuned for: at 560 px the same constant renders about 14 px, and from 561 to about 960 px of window nothing changes — the 768 px tablet, the split detail pane and a narrow desktop window keep 5–8 px labels (table). Dropping two values costs the reader the 25 % and 75 % gridlines' figures.
  • Why A: the defect is not a phone defect but a scale defect — the label shrinks continuously below a 960 px chart — and A answers it at every width with the number the spec already states. Its cost is a few lines in a hook that exists. The "Daten als Tabelle" disclosure stays the fallback that lets 9 px stand (Accessibility Floor → Charts); A keeps the floor's premise true instead of relying on it harder.
  • Not drawn: a bigger token (10 or 11 px). A changes where the size is measured, not the size; on a 1440 px desktop the labels go from about 11 to 9 px (table). If the owner wants today's desktop size kept, the rule becomes a floor — calc(9px * max(1, var(--chart-upx, 1))) — one word in the story.
