Grade: Poor — six critical findings. Grade is derived from severity counts alone: the rubric walker was deselected for this run, so no dimension verdicts were produced.

This PRD is a strategy memo wearing a requirements document's clothes. Its central factual claim — that transaction-grade German-bank data is "locked in PDFs" — is stated in §2 as "The hard truth about source data" and then contradicted 100 lines later by its own OD-2, which asks someone to go "verify empirically what comdirect actually exports as CSV" and tags the whole question [ASSUMPTION]. That unverified premise is the sole justification offered for ADR-0021, which has already been Accepted and has already amended AGENTS.md to punch a hole in a hard rule. The PRD also never mentions that the authoritative PRD's own FR-17 documents "comdirect: depot positions and transactions via the official REST API" — the option that would make Feature D unnecessary is not rejected, it is simply absent from the analysis.

Below the strategy layer the requirements do not survive contact with the codebase. Feature B has no legal home: holdings are never stored (ADR-0004), the kind set is closed and has no positions-snapshot kind, and FR-6 forbids the one remaining implementation — three doors, all locked, and the PRD notices none of them. Feature A maps columns but never values, so it cannot map "Wertpapierkauf" onto a closed kind set, and says nothing about decimal commas, ; delimiters, DD.MM.YYYY dates or CP1252 encoding. FR-4's idempotency claim is false for the ordinary re-import cases. There are zero acceptance criteria, so the document cannot pass the ADR-0026 decision gate it needs to start an epic batch, and the addendum.md its header promises does not exist. Finally it is a month stale: FR-14's export was cancelled 2026-07-22, and ADR-0029 now binds every import path it describes.

Cynical review, 2026-07-25, against prd.md (status draft, unchanged since 2026-06-21). critical

The founding premise is asserted as fact and admitted as unverified in the same document

§2 / §6 OD-2
§2 uses the rhetoric of settled fact ("the hard truth") for a proposition §6 explicitly parks as unverified. That proposition is the entire load-bearing argument for Feature D, which has already become ADR-0021 (Accepted) and already amended AGENTS.md. The project now carries a permanently widened document-intake surface, a per-broker maintenance obligation and a pending new dependency — all justified by a premise nobody has checked, where checking costs one afternoon and one export click. §9 even ranks the verification as step 2 while the irreversible decision was taken at step 0.
Fix: Demote §2 to "Working hypothesis, unverified (OD-2)" and state plainly that ADR-0021 was accepted before OD-2 closed. Add a re-open trigger: if OD-2 shows transaction substance via CSV or the official API, ADR-0021's Option A/B choice is re-litigated before the first Feature D story. Move OD-2 to step 1 of §9.
critical

The option that would make Feature D unnecessary is documented in the main PRD and never mentioned here

§2 / Feature D / §4
The authoritative PRD's FR-17 says "comdirect: depot positions and transactions via the official REST API", listed under Phase 3 as an "operator-stated must-have — the gate governs when and how, not whether". This PRD neither cites nor rejects it; §4 disposes of it as "unchanged policy". ADR-0021's options analysis inherits the blind spot, weighing only in-app parsing against out-of-app push, never the official API. The project may be about to build and perpetually maintain a hostile-input PDF parser to recover data an authenticated REST endpoint returns as structured JSON.
Fix: Add a "Considered and rejected" subsection covering the REST API with the real reason — most plausibly history depth and the PhotoTAN/unattended problem already logged as main-PRD OQ-6. Reconcile §4's "unchanged policy" wording. Fold the result back into ADR-0021 as a third rejected option.
critical

Feature B has no legal representation in the ledger and contradicts itself

Feature B / FR-5, FR-6, FR-7
Three ways to implement FR-5, all closed: storing positions is forbidden (ADR-0004, no holdings table exists); synthesizing deliveries is forbidden by FR-6's own "never silently fabricates transactions"; adding a ledger kind is unmentioned and would be an ADR-grade change to a closed 15-kind set where unknown kinds raise by design. The one snapshot concept that exists, balance_adjustment, is cash-only. FR-6 and FR-7 then presuppose the impossible thing happened. The path of least resistance for an implementing agent is exactly the forbidden holdings table.
Fix: Decide the representation in this PRD. Invariant-safe options: (a) a transient, never-persisted reconcile input — which ADR-0029 §6 has since built as POST /api/v1/holdings/reconcile, making FR-7 largely redundant; or (b) explicit user-confirmed conversion to inbound_delivery with no cost basis, which requires deleting FR-6's clause and stating the cost-basis consequence. Pick one; do not ship FR-5 as written.
critical

FR ids collide head-on with the authoritative PRD's stable global numbering

§5 (all FRs) / §8
The authoritative PRD states the rule: "IDs are stable and globally numbered; new requirements append, never renumber." This PRD restarts at FR-1 and collides across the whole range — its FR-5, FR-7, FR-11/12, FR-13/14 all mean something else in the main PRD. Not cosmetic: "FR-7" is cited across the live corpus in its main-PRD meaning (ADR-0029 uses it repeatedly), and §8 of this very document demonstrates the confusion by using FR-14 in both senses within four lines.
Fix: Renumber into the global sequence (continuing past the highest allocated id) or prefix unambiguously (FR-DI-1 …). Fix §8's "#355 / FR-14" and FR-8's cross-reference to name the main-PRD id explicitly. Add a line to §5 stating which numbering authority governs.
critical

Feature A maps columns but never maps values — it cannot produce a transaction kind

Feature A / FR-1
Mapping the type field to a source column is nowhere near sufficient. That column holds free text in the broker's vocabulary — "Kauf", "Wertpapierkauf", "Dividendengutschrift", "Vorabpauschale", "Depotübertrag Eingang" — and must land on one of exactly 15 closed kinds where an unrecognised value raises by design. Feature A gives the user no way to express "the string Wertpapierkauf means buy", so it cannot import a single row of any real broker CSV, which is its entire purpose. Same gap for "account" (a buy touches depot and cash account) and for security resolution.
Fix: Split FR-1 into column mapping and value mapping: a per-source dictionary from distinct source values to Portfolixir kinds, with unmapped values blocking apply and surfaced in preview, never defaulted. Require account mapping to resolve depot and cash account separately, and security resolution to run the ADR-0029 §2 ladder.
critical

FR-4's idempotency claim is false for the cases that actually occur

FR-4 (and FR-11, FR-15)
Idempotency is two-layered (#533): a per-record import_hash plus a formatting-tolerant dedup_key/1 computed over the resolved database identity. Because layer two keys on resolved ids, Feature A breaks it in the ordinary case: a user who corrects a mapping and re-imports the same file changes the resolved ids and silently duplicates every row — and FR-2's savable mappings make that the designed workflow. Also unaddressed: partially overlapping re-imports, corrected exports (silent double-booking), and what the hash covers for a PDF whose bytes differ but economics do not. AGENTS.md classes import idempotency as a risk tier requiring dedicated PRs with real human review; a one-line parenthetical is not a specification.
Fix: Replace FR-4 with explicit semantics — state the two layers, then add requirements for (a) re-import after a mapping change: preview shows which rows newly insert because resolution changed, with explicit confirmation; (b) partial overlap: only non-duplicates insert, duplicates reported; (c) corrected rows produce a conflict in preview, not a silent second booking; (d) PDF intake hashes extracted economic records, never file bytes. Add ADR-0029's preview→apply revalidation.
high

§4's out-of-scope wording silently widens the document-intake exception to binary .portfolio

§4 Scope
Scope defined by complement, on an [ASSUMPTION] tag, against a hard rule. Read literally, "non-PP non-PDF document formats remain out" puts everything that is a PP format and everything that is a PDF in scope — pulling in the two things both governing documents explicitly keep out. The PRD then acts on its own widened reading at FR-16 ("Evaluate PP XML full import"), with no mention that the main PRD attaches a scope gate to exactly this.
Fix: State scope positively. List in-scope intake formats explicitly (PP CSV/JSON v1; delimited broker CSV; broker PDFs per ADR-0021) and out-of-scope ones explicitly (binary .portfolio — hard out; PP XML — gated on ADR + AGENTS.md amendment). Remove the [ASSUMPTION] tag from a scope boundary.
high

Feature C opens a bulk write path with no audit, authorization or validation story

Feature C / FR-8, FR-9, FR-10
"Auditable" is asserted and never specified — the audit journal (ADR-0017, main-PRD FR-28), whose stated purpose is precisely this threat, is never named. epics.md even fixes the ordering ("MCP writes must be journaled"), which §9 ignores. Authorization is absent: a single shared bearer token, no scopes, no per-actor identity, on an instance whose web UI is unauthenticated by design. Validation is asserted by omission. And FR-9's idempotency keys introduce a second, incompatible idempotency mechanism with no statement of precedence — two idempotency systems that do not know about each other is how double-booked ledgers happen.
Fix: Require that every API/MCP write is journaled per ADR-0017 with actor recorded, and make Feature C depend on that work; state as a testable requirement that API writes run identical changeset validations; define the write authorization model or record it as an open decision; specify how idempotency keys relate to content-hash idempotency (keys dedupe the request, hash dedupes the records, both must hold); specify partial-failure semantics and adopt ADR-0029's fail-closed rule for non-interactive paths.
high

Feature A ignores every property a real German broker CSV actually has

Feature A / FR-1, FR-3
"Any delimited file" is the whole parsing specification. Absent: decimal separator (1.234,56 — and Decimal.new/1 raises on that string), thousands separator, date format, character encoding (CP1252 is routine; mis-decoding silently corrupts security names, which are a matching tier in ADR-0029), delimiter detection (; is the German default because the comma is the decimal mark), preamble lines, quoted fields, and negative-signed amounts. That last is a direct invariant collision: amounts are positive magnitudes with sign from the kind, and broker CSVs carry signed amounts — so every sell row either fails the changeset or is stored with a forbidden sign. The API escape hatch ("locale parsing is the client's job") is unavailable for a file upload.
Fix: Add a per-source format profile — encoding, delimiter, quote char, decimal and thousands separators, date format, header row offset — detected with a preview, user-overridable, saved alongside the mapping. Add explicit sign normalization mirroring the PP importer. Require the preview to show parsed Decimal values, and ambiguous parses to block rather than guess.
high

Feature D drops binding ADR-0021 constraints and calls an undefined thing "sandboxed"

Feature D / FR-11, FR-12a
ADR-0021 requires parsed records to go through an atomic, content-hash-idempotent apply recorded in the audit journal, and imposes a per-change parser security review — FR-11 mentions neither. "Sandboxed" appears twice and is never defined; Elixir provides no process sandbox, so the word backs no mechanism. The named threats are the easy ones; the ones that actually kill PDF parsers are missing — decompression bombs, XRef and object-reference cycles, recursion depth, malformed length fields, memory exhaustion. Sobelow is a Phoenix static analyzer; nominating it for a binary-format parser is a category error. The dependency is hand-waved: mix.exs has no PDF dependency and no candidate is named, and the realistic Elixir option is shelling out to pdftotext — a materially worse posture than "a library".
Fix: Require PDF-derived records to be journaled and idempotent over extracted economic records; define "sandboxed" by naming the isolation boundary (separate OS process, no network namespace, memory and wall-clock rlimits, hard page cap) with numeric limits so FR-12a is testable; add the missing threat classes as named rejection cases with malformed synthetic fixtures; name the candidate library or binary and address the shell-out case; restate the per-change security-review obligation; schedule the dependency decision as its own PR before any Feature D story.

high

The PRD predates ADR-0029 and describes import paths that violate it

Features A, B, C, D
ADR-0029 (Accepted 2026-07-22) makes binding on every import path: the security identity ladder with exactly-one-candidate tiers and a stronger-identifier veto; preview→apply revalidation aborting whenever resolution differs from what was approved; config-at-risk warnings with per-row acknowledgment; a pre-apply inverse check; and fail-closed behaviour for non-interactive paths. This PRD offers only "preview shows the records that would be created" — a strictly weaker contract. An importer built to FR-3 will silently duplicate securities and strand the classification and target configuration ADR-0029 exists to protect.
Fix: Add a cross-cutting requirement that every intake path resolves securities through the ADR-0029 §2 ladder and inherits preview→apply revalidation, config-at-risk acknowledgment, the inverse check and fail-closed behaviour. Bump updated: and add ADR-0029/ADR-0030 to the reference list.

The PRD reverts the main PRD's deliberate anonymization and asks for a real bank file

frontmatter / §3 / OD-2 / FR-11
This is a public repository. AGENTS.md forbids committing "the maintainer's personal banking relationships: which banks/brokers hold their accounts" and requires generic placeholders. medium

Success metrics and the counter-metric are unmeasurable as written

§7
CM-1 counts silent wrong-data incidents — unmeasurable by construction: if the failure were observable it would not be silent, and no detector, sampling procedure or reconciliation baseline is proposed. SM-1 has no oracle for "correct" and cannot be exercised in CI, since synthetic fixtures and no-network are mandated — so it is verifiable exactly once, manually, by the one person with the account. SM-2 has no baseline, target, instrument or start/stop events, and with a user population of one any measurement is a single anecdote.
Fix: Give SM-1 an oracle: "a synthetic broker CSV/PDF fixture pair imports to holdings matching a checked-in Decimal-exact expectation" — testable in CI, mirroring the golden-master approach already on the quality-gate roadmap. Give SM-2 a baseline and target or cut it. Replace CM-1 with something observable (zero rows applied that failed validation; each confirmed wrong-number incident becomes an invariant test; a reconciliation count from the ADR-0029 §6 endpoint).

medium

FR-15's partial-apply requirement contradicts the atomicity it claims to preserve

Feature F / FR-15
"Atomic" and "some rows are skipped" are reconcilable — one transaction commits the valid subset — but only if the PRD says so, and it does not. Nor does it say what happens next: are skipped rows remembered? Does re-importing after fixing the source re-offer them, and how does that interact with FR-4? Is skipping a per-row user decision or an automatic policy? And is a zero-amount tax record invalid at all, or is that a validation bug to fix rather than a row to skip — the example given reads more like the latter.
Fix: State that apply commits the approved subset in one transaction and records skipped rows in the import result. Specify that a later re-import re-evaluates skipped rows against the dedup key. Separate "invalid data the user must fix" from "records Portfolixir wrongly rejects" — the zero-amount case belongs in the second bucket and is a validation fix, not a skip feature.
medium

The PRD has no non-functional requirements, though the decision log claims it does

whole document / §5
The decision log says constraints landed as "NFR-equivalent notes". There are none. §4 mentions two of three constraints in a parenthetical and never mentions Decimal at all — in a PRD whose entire subject is getting numbers into a ledger from sources that format numbers differently. Also absent: upload size and row-count limits; where uploaded files are stored and whether they are deleted after apply (a Wertpapierabrechnung is sensitive personal data sitting on disk); and any performance expectation, despite main-PRD NFR-8, which a preview rendering a full import would violate.
